# Налаштування перевірки (`checks.yaml`)

Засіб перевірки викладача звертається до запущеного стенда як зовнішній клієнт. Він читає два
файли проєкту. З `openapi.yaml` він бере маршрути, ролі операцій і приклади тіл, а з
`checks.yaml` – те, чого в контракті немає. Скопіюйте [checks.example.yaml](../checks.example.yaml)
як `checks.yaml` у корінь проєкту поруч з `openapi.yaml`.

## Пункти (`items`)

Номери пунктів беруться з методички ЛР. Пункти з позначкою «Ядро» перевіряються завжди, їх у
`items` не пишуть. У `items` перелічують лише виконані пункти поза ядром. Невдала перевірка
невибраного пункту дає SKIP, а не FAIL. Невідомий номер зупиняє запуск. Літери можна писати
кирилицею (`О1.5`, `Д2.6`) або латиницею (`O1.5`, `D2.6`).

```yaml
items: [О1.5, О2.2, Д2.6]
```

## Що засіб бере з контракту

Службові маршрути (`/health`, `/metrics`, `/metrics/prom`) однакові для всіх тем. Залиште їх
такими, як у [openapi.example.yaml](../openapi.example.yaml). Маршрути `/v1` вимагають
`Authorization: Bearer <API_TOKEN>`. Токен викладач передає засобу під час запуску.

Роль предметної операції позначають полем `x-course` в описі операції:

| `x-course` | Операція | Без позначки визначається як |
|---|---|---|
| `receiver` | приймання операції в чергу | `POST` із відповіддю 202 |
| `request-state` | стан прийнятої операції | лише позначкою |
| `resource-state` | стан ресурсу з полем інваріанта | лише позначкою |

Тіло запиту приймача засіб бере з прикладу `normal` (`examples`) операції `receiver`. Значення
в ньому мають бути в демоданих проєкту, наприклад філія `central`. Рядок `{uuid}` у прикладі
в кожному запиті стає новим ідентифікатором.

## Приклад

У прикладі «Міська бібліотека» книгомат подає повернення `POST /v1/returns` (`x-course: receiver`).
Сервіс ставить його в обмежену чергу, а обробник записує книжку на полицю сортування філії в
PostgreSQL. Стан полиці повертає `GET /v1/shelves/{branch_id}` (`x-course: resource-state`).
Відповідь містить `capacity`, `used`, `books` і поле `invariant_ok`, що показує, чи виконано
інваріант «used дорівнює кількості книжок і не більший за місткість».

Цей маршрут потрібен для пункту О1.4. Засіб створює навантаження через `receiver` із прикладом
`normal`, потім читає стан ресурсу й перевіряє інваріант. Із контракту засіб не дізнається двох
речей. Шлях містить параметр, і засіб не знає, яку саме полицю читати. Крім того, він не знає,
яке поле відповіді містить результат перевірки інваріанта. Тому обидва значення задають у
`checks.yaml`.

```yaml
resource:
  path: /v1/shelves/central
  ok_field: invariant_ok
```

Полиця `central` має бути в міграції з демоданими, а приклад `normal` у `receiver` має подавати
повернення саме в цю філію (`branch_id: central`). Інакше навантаження й перевірка стосуватимуться
різних ресурсів. Те саме поле інваріанта засіб використовує й після керованої відмови в О3.4.

Так само заповнюють решту розділів. Наприклад, для звіту ЛР4 у `reports.keys` перелічують поля,
за якими ваш звіт групує рядки (`branch_id`, `day`), а в `reports.field` – поле відповіді з цими
рядками. За ними засіб порівнює звіт з еталоном.

## Ключі `checks.yaml`

Усі ключі необов'язкові. Задавайте лише ті, що відрізняються від типових значень.

| Ключ | Що задає | Звідки взяти |
|---|---|---|
| `items` | вибрані пункти поза ядром | методичка ЛР |
| `roles` | роль, метод, шлях і приклади операції, якщо `x-course` не використано | ваш `openapi.yaml` |
| `services` | імена сервісів, якщо їх змінено | `compose.yaml` |
| `load_s` | тривалість навантаження ЛР1 у секундах (типово 10) | на ваш розсуд |
| `resource` | `path` – маршрут стану тестового ресурсу, `ok_field` – поле інваріанта (О1.4, О3.4) | ваш `openapi.yaml` і демодані |
| `metrics` | імена метрик черги, оброблення й відхилень у `/metrics` (О1.5) | ваш `metrics.gauge(...)` |
| `compute` | `tolerance` (відносна похибка), `bench_n`, параметр і значення режимів спільної суми, поля тіла для асинхронного розрахунку (ЛР2) | ваш маршрут розрахунку |
| `histogram` | запити для одного й багатьох процесів, поле для порівняння (Д2.5) | ваш маршрут гістограми |
| `reports` | поле стану задачі, поле рядків, ключі групування, похибка, службові поля (ЛР4) | ваш маршрут звіту |
| `panel` | поле вікон, ключі вікна, службові поля (ЛР5) | ваш маршрут панелі |
| `coordinators` | значення власника ролі → сервіс координатора (ЛР6) | ваш формат ролі в etcd |
| `lease_ttl_s` | строк оренди ролі в секундах (ЛР6) | ваша реалізація координатора |
| `history` | `check` – маршрут перевірки історії, `ok_field` – поле результату (О6.3) | ваш `openapi.yaml` |

У звітах і панелі порівнюються всі поля рядків. `ignore_fields` виключає лише службові поля,
наприклад `batch_id` чи `written_at`. Ключі групування й обчислені показники виключати не можна.
