# Розподілені та паралельні обчислення – каркас проєкту

Каркас проєкту курсу «Розподілені та паралельні обчислення». Приклади контрактів і даних описують повернення книг у міській бібліотеці: сервіс приймає операції, виконавці обробляють їх, аналітичні задачі формують результати.

`api` надає HTTP-інтерфейс. PostgreSQL зберігає стан. Ray призначений для розподілених задач,
Spark – для пакетних і потокових обчислень, Kafka – для потоку подій, etcd – для координації.
Предметні маршрути, обчислення й координатори містять `TODO`. Це заготовки, а не реалізований проєкт.

## Запуск

Потрібні Docker із Compose v2 (пам'ять для Docker – 10–12 ГБ для всіх сервісів), Python 3.14 і
[uv](https://docs.astral.sh/uv/) для інструментів. Команди виконуються з кореня каталогу курсу.

```sh
cp .env.example .env
docker compose up -d --build
docker compose ps
curl -i http://localhost:8000/health
```

Якщо пам'яті бракує, зупиніть те, що зараз не потрібно. Наприклад, у ЛР1–2 це робить команда
`docker compose stop spark-worker-1 spark-worker-2 spark-runner spark-history stream ray-worker ray-worker-extra`.

Запуск надає інфраструктуру й службові маршрути каркаса, але не готову предметну систему.
Щоб створити таблиці й тестові дані прикладу, скопіюйте `migrations/examples/*.sql` у `migrations/` і
виконайте `docker compose run --rm migrate`.

| Що | Адреса |
|---|---|
| `api` (токен `dev-token`) | http://localhost:8000 |
| PostgreSQL (`app` / `app`, база `app`) – для pgAdmin чи іншого клієнта | localhost:5433 |
| панель Ray | http://localhost:8265 |
| Spark: головний вузол, задача звіту, потокова задача, сервер історії | :8280, :4040, :4041, :18080 |
| Kafka з хоста, Kafka UI | localhost:9095, http://localhost:8185 |
| etcd | localhost:2379 |
| вебклієнт (поза Compose) | http://localhost:8083, запуск `python -m http.server 8083 --bind 127.0.0.1 --directory client` |
| Prometheus, Grafana | :9091, :3001 |

Порти не перетинаються з портами комплекту Web. Їх можна змінити в `.env`.

## Дані для Spark

Команди виконуйте з кореня цього комплекту. Потрібен Python 3.14.
Генератори допомагають підготувати дані за карткою, а предметні обчислення
в `spark/jobs/report.py` та `spark/jobs/stream.py` реалізує команда.

### Історія для ЛР4

[Генератор історії](tools/generator/generate_history.py) створює таблицю фактів
і довідник у Parquet за [описом полів](tools/generator/spec.example.json).
Власні залежності між полями можна задати функціями, як у
[прикладі тривалості позики та штрафу](tools/generator/columns.example.py).

```sh
uv run tools/generator/generate_history.py tools/generator/spec.example.json --out data --extend tools/generator/columns.example.py
```

`--rows` змінює кількість фактів, `--jobs` – кількість процесів генерації.
За однакових опису, `seed`, коду та версій залежностей набір відтворюється.
Кількість процесів не змінює дані. Повторний запуск замінює частини таблиці
фактів у вказаному каталозі. Невеликого набору достатньо для перевірки звіту.
Великий потрібен для окремого дослідження продуктивності.

### Події для ЛР5

[Генератор подій](tools/generator/generate_events.py) записує JSONL у порядку
надсилання. [Приклад опису](tools/generator/events.example.json) задає поля,
`seed`, початок і тривалість періоду та кількість подій за хвилину.
Види полів наведені в [columns.py](tools/generator/columns.py). Поле `ref` призначене
лише для історії. Власні функції полів підключаються через `--extend FILE`.
Вони мають використовувати переданий генератор випадкових чисел `rnd`.

```sh
uv run --no-project --python 3.14 python tools/generator/generate_events.py tools/generator/events.example.json --scenario normal --out normal.jsonl
uv run --no-project --python 3.14 python tools/generator/generate_events.py tools/generator/events.example.json --scenario late --out late.jsonl
uv run --no-project --python 3.14 python tools/generator/generate_events.py tools/generator/events.example.json --scenario duplicates --out duplicates.jsonl
```

За однакових опису базових даних і `seed` ці три сценарії використовують
ті самі події з незмінними ідентифікаторами, полями й часом події (event time).
Ім'я сценарію не впливає на випадкові числа. Затримки й повторення мають
окремі генератори випадкових чисел, незалежні від генерації даних.
Інший `seed` змінює випадкові значення, але не робить послідовні ID унікальними
між наборами. За однакових опису, `seed`, коду та версій залежностей
набір відтворюється. Зберігайте файли досліду для повторного використання.

| Сценарій | Що змінюється |
|---|---|
| `normal` | Події надсилаються за часом події |
| `late` | `late_share` задає частку затриманих подій, `late_minutes` – діапазон затримок; змінюється порядок доставки |
| `duplicates` | `duplicate_share` задає частку подій, для яких додається точна копія з тим самим ID |
| `boundary` | Додаються події на межах інтервалів від `start` із кроком `window_minutes` та за 1 мс до них; базові події зберігаються, додані ID мають префікс `boundary-` |

Параметри затримок і повторень можна поєднати в одному описі сценарію.
Для `boundary` узгодьте `start` із початком вікон вашої задачі Spark.
Цей сценарій додає нові події, тому його підсумки не мають збігатися з `normal`.
Частки визначають імовірність вибору, а фактичні кількості генератор друкує після
запису. Лічильник `late` означає штучно затримані події, а не події, які Spark
відкинув. JSONL зберігає порядок доставки, а розраховані затримки не є паузами
реального часу. Надсилання виконує окремий засіб.

```sh
uv run tools/jsonl_to_kafka.py normal.jsonl gate-events --key gate_id --pace-ms 5
```

Тему Kafka та поле ключа узгодьте зі своєю карткою. `--pace-ms` задає паузу між
повідомленнями. Для керованого порівняння О5.3 використайте одну партицію Kafka
або інший обґрунтований спосіб контролю порядку, як вимагає методичка.

Опис `tick` додає останньою службову подію з часом
`start + minutes + after_minutes`. Її потрібно врахувати для просування
межі часу подій (watermark), але не зараховувати до предметного показника.
Виберіть її час достатньо пізнім для фіналізації останнього вікна з вашим
допустимим запізненням. Саме надсилання `tick` ще не підтверджує фіналізацію.

### Контрольний приклад і порівняння

[Контрольний JSONL](tools/generator/control/events.jsonl) містить шість проходів
через два турнікети та завершальну службову подію. У
[відомому результаті](tools/generator/control/expected.json) наведено кількість
входів і виходів для кожного турнікета у двох 15-хвилинних вікнах UTC.
Початок вікна включено, кінець – ні. Тому `08:14:59.999` належить першому вікну,
а `08:15:00.000` – другому. Службова подія не збільшує лічильники.
Це приклад перевірки інструмента й меж вікон. Предметний пакетний розрахунок
за О5.5 для своєї теми реалізує команда.

- Для О5.1 порівняйте базовий набір із тим самим набором із повтореннями.
  Після усунення дублів у визначеному часовому горизонті результати мають збігтися.
- Для О5.3 збережіть один `late.jsonl` і повторно подайте саме його з двома
  значеннями допустимого запізнення. Збережіть однакові порядок та умови подання.
  Точний перелік відкинутих подій визначайте за виконанням Spark, а не лише
  за параметрами генератора, бо на нього впливають також мікропакети та просування watermark.
- Для О5.5 порівнюйте потік із пакетним розрахунком того самого набору,
  коли всі перевірювані події надходять у межах допустимого запізнення.
- Незалежні досліди починайте з ізольованими входом, checkpoint і результатами,
  щоб попередні ID, зміщення Kafka та watermark не впливали на новий дослід.
  Для перевірки відновлення О5.4, навпаки, збережіть той самий checkpoint.
  Генератор не очищає Kafka, базу або контрольні точки.

В окремому DPC-проєкті генератор може відтворювати події відсутньої частини
за карткою. У спільному проєкті дії, що змінюють стан Web, проходять через
його API. Штучні аналітичні події не замінюють підтверджених операцій Web.
Для показників стану на контрольний момент задайте початковий стан і допустимі
переходи своєї теми, бо незалежний випадковий вибір полів цього не забезпечує.
Допоміжний засіб і контрольний приклад не додають критеріїв оцінювання.
